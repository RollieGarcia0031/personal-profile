# Tracks Data Source (`content/tracks.json`)

This project treats `content/tracks.json` as the **single source of truth** for track metadata.

It powers two different outputs:

1. the `/tracks/` listing page (client-side render + filter/sort), and
2. generated `/track-info/:id/` detail pages (build-time HTML generation).

---

## Why this file is important

`content/tracks.json` is the center of the track system because it keeps display data in one place:

- If a field changes (title, cover image, duration, etc.), both list and detail experiences can reflect that change.
- Every track uses its `id` as a stable identifier:
  - for linking from `/tracks/` cards to `/track-info/:id/`, and
  - as the output folder name generated by `scripts/generate-track-info.mjs`.
- Build reliability depends on it. The generator validates required fields (`id`, `title`, `audioSrc`) before writing pages.

In short: if `tracks.json` is accurate, the whole tracks experience stays consistent.

---

## How `/src/tracks/index.html` renders tracks

`src/tracks/index.html` provides the page shell and controls (`search`, `sort`, and grid/list buttons). The actual track cards are injected into `#tracks-grid` by `src/tracks/main.js`.

### Rendering flow

1. `main.js` imports `content/tracks.json` directly as `DATA_JSON`.
2. A page state object is initialized:
   - `allTracks`: full dataset
   - `visibleTracks`: filtered/sorted result
   - `filters`: search term + selected sort mode
3. A lightweight pub/sub store (`createPubSub`) coordinates updates.
4. On filter changes:
   - tracks are filtered by a searchable text blob (`title`, `description`, `genre`, `writer`, `id`)
   - then sorted by the selected field (`title`, `date`, or parsed `duration`)
5. The render subscriber replaces children of `#tracks-grid` and creates one `<track-option>` per visible track.
6. Each `track-option` receives attributes from JSON fields (id/title/description/genre/audio/img/duration/bpm/date).

### What makes `id` critical on the listing page

The custom element template builds a `Listen` link as:

- `/track-info/${track_id}/`

So if `id` changes in `tracks.json`, the list page navigation target changes too.

## How `scripts/generate-track-info.mjs` generates detail pages

`generate-track-info.mjs` is a build-time content generator.

### Generator flow

1. Reads and parses `content/tracks.json`.
2. Validates the root is an array.
3. Deletes and recreates `src/track-info/`.
4. For each track:
   - validates required fields (`id`, `title`, `audioSrc`)
   - creates `src/track-info/<id>/`
   - writes `src/track-info/<id>/index.html` using `renderPage(track)`
5. Logs how many pages were generated.

### Safety details

- `escapeHtml()` is used before injecting user-facing string content into the generated HTML.
- Optional fields are given fallbacks (`''` or `undefined`) so missing metadata does not crash generation.

### Build integration

`package.json` wires generation into the build:

- `pnpm generate:track-info` → runs the generator manually.
- `prebuild` runs `generate:track-info` automatically before `pnpm build`.

That ensures `/track-info/` HTML stays in sync with `tracks.json` during builds.

## `tracks.json` field guide

Typical track object structure:

- `id` (string, required): unique slug, folder name for generated page, URL key.
- `title` (string, required): display title.
- `audioSrc` (string, required): audio URL used on cards/detail page.
- `description` (string): summary for card/detail.
- `genre` (string): shown in card and detail header area.
- `imgSrc` (string): cover/backdrop image path.
- `date` (string): sortable release-like value (works best in `YYYY-MM-DD`).
- `duration` (string): expected `mm:ss` for duration sorting.
- `bpm` (number): shown in detail metadata card.
- `instruments` (array of strings): listed in detail page.
- `writer` (string): creator credit.
- `story` (string): long-form track background.

## Content maintenance rules

When editing `content/tracks.json`, keep these rules to avoid broken UX:

- Keep every `id` unique and URL-safe (slug style).
- Always include required fields: `id`, `title`, `audioSrc`.
- Keep `duration` in `mm:ss` so duration sort behaves as expected.
- Prefer ISO-like `date` (`YYYY-MM-DD`) for predictable ordering.
- Ensure asset paths (`audioSrc`, `imgSrc`) point to valid files under `src/public/...` (or deployed equivalents).

After changes:

1. Run `pnpm generate:track-info`.
2. Run `pnpm dev` and verify:
   - `/tracks/` list renders/searches/sorts correctly
   - each `Listen` link opens the expected `/track-info/:id/` page.
